## A request has to be checkable

A prompt is not a spell. It is the task statement for this turn. The practical test is specific: someone who missed the earlier discussion can read only this text and still say where to start, what done means, and what must not move.

“Optimize this” or “refactor this” leaves the standard with the model. It will pick a common direction that looks reasonable. That direction may not be yours.

## Four sentences are enough to start

Write them in this order, and make each one pointable:

1. Goal: the visible result this change should produce.
2. Current behavior: what the behavior or the code does now.
3. Constraints: what must stay, and what you are explicitly not doing.
4. Check: how you will look, including one happy path and one easy failure.

### Rewrite a vague request into those four

The vague line is: “Search is a bit broken, please fix it.”

Add an observation first. For example: while typing Chinese, Enter confirms an IME candidate and the page opens search results. The desired behavior is that confirming a candidate does not search, and a later Enter submits the search. The constraint is to leave the result page’s styling alone and add no dependency.

You can hand the model this block:

```text
Goal: Confirming an IME candidate must not open search results.
Current: On the course search box, Enter during composition opens the result page.
Expected: Enter commits the candidate; a later Enter submits the search.
Constraints: Keep the result page and its URL. Add no dependencies.
Check: Type a Chinese query, confirm the candidate, then submit. Both steps should match the expected line.
```

There is no “you are an expert” filler. A role slogan takes space and cannot be checked. `Enter` appears twice, once to confirm and once to submit. That is the edge.

<Callout title="Ask for a restatement first" type="info">
Before any edit, ask the model to restate the task in your four sentences. If the restatement drops a constraint or the check, fix the prompt before you fix code.
</Callout>

## Describe the symptom more than the patch

If you do not yet know which function to change, do not name a guessed file in the prompt unless you have already confirmed it. State the symptom, the expected behavior, and the constraints, and let the model point at the location. Read that location before you allow an edit.

A prompt may be short. Short means no empty politeness and no repeated background, not less information. Agreements that are true on every task belong in rules, not piled into this prompt. A limit that is true only this once should not become a permanent rule, or it will clip a later task.

## Try it

Take a sentence you recently said to an AI and rewrite it as goal, current behavior, constraints, and check. Read it back. If one of the four cannot be observed, it is not ready to send. Save the rewritten block. Later lessons will use it as context and as the check.
