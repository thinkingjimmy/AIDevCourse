## 把生成结果当作待检查的改动

AI 可以帮助完成代码，也可能误解需求、遗漏边界，或把相关文件之外的行为一起改变。你的工作不是逐行重写它的答案，而是判断这次修改是否真的满足了目标。

本课会用三层检查建立证据：先看范围，再试行为，最后运行项目适用的自动检查。

## 第一层：检查差异范围

打开编辑器里的文件差异。先看文件列表，再看具体修改。每一处变化都应该能对应到任务需求或必要修复。

| 检查问题 | 为什么要问 |
| --- | --- |
| 是否改到了预期文件？ | 排除修改了另一个相似页面 |
| 是否出现无关配置变化？ | 避免把环境调整混入功能修改 |
| 是否删掉了原有分支？ | 防止正常路径成功、边界却退化 |
| 是否新增了依赖？ | 确认它确实必要且符合项目约定 |

如果某段改动的意图不清楚，可以让 AI 用一个具体输入和输出解释。解释仍无法对应需求时，要求缩小范围。

## 第二层：亲手试一遍行为

用实际页面执行任务的主要流程，再覆盖一个容易失败的情况。对于按钮文字修改，检查显示和点击；对于继续学习，分别检查无记录、有记录、最近课时已完成的情况。

不要只检查顺利路径。试着使用键盘，在窄窗口里打开页面，刷新后再次操作。需要保存的状态，应在刷新或重新进入后核对，而不是只看当前画面。

## 第三层：运行项目已有检查

先阅读项目 README，找到已经配置的检查命令。不同项目的脚本不同，不要把下面的示例直接当成所有项目都支持的命令：

```bash
pnpm check
pnpm build
```

上面的命令只有在项目 package.json 定义了相应脚本时才适用。保留实际输出和退出状态；命令没有执行、执行中断或环境阻塞，都不能写成“已通过”。

<Callout title="测试通过也需要检查目标" type="info">
自动检查只能覆盖它已定义的条件。按钮跳错目的地但语法正确，构建仍可能成功，所以行为验证不能省略。
</Callout>

## 失败时一次缩小一个变量

记录第一条有用的错误信息，以及触发错误的步骤。先确认问题可复现，再请 AI 解释可能原因和准备修改的位置。不要一边改代码、一边升级大量依赖，这会使原因更难判断。

修复后重新运行失败的检查，并回归受影响的主要行为。重复与当前修改无关的全量检查没有额外价值，但也不要用缩小检查范围来掩盖尚未解决的问题。

## 留下可以复核的完成记录

用简短记录说明三个事实：修改了什么、实际执行了哪些验证、还存在哪些限制。示例：

```text
Changed: the primary link now says Start learning.
Checked: label, destination, keyboard activation, and the project build.
Remaining: mobile Safari has not been checked on a physical device.
```

## 动手练习

取上一课写出的任务，将每条验收条件转换成一个实际操作。完成修改后逐项填写观察到的结果，而不是预测结果。只有这些证据足以说明目标已满足，才把任务标记为完成。
