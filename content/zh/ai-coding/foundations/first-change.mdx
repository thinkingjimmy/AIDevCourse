## 先把任务缩小

第一次与 AI 一起写代码，最重要的不是一次做出完整产品，而是走完一个能解释清楚的闭环：提出目标、检查修改、验证结果。选择一个你已经能运行的页面，例如一个只有标题和按钮的练习页面。

本课的目标是修改按钮文字，保留原来的点击行为。这个任务足够小：你能在页面上直接看到结果，也能通过点击确认原有功能是否仍然有效。

![一次小修改的协作流程：目标、上下文、修改和验证](/images/courses/change-cycle.svg)

## 描述一个可以验收的目标

“帮我优化页面”没有说明什么叫更好。换成“把主按钮文字改为 Start learning，保留点击后进入课程列表的行为”，AI 就有了明确边界。

可以直接使用这样的任务描述：

> Find the primary learning button. Change its visible label to “Start learning”. Keep its destination and all other behavior unchanged. Explain which file you changed and how you checked the result.

提供任务时，同时告诉 AI 你在哪个页面看到这个按钮。如果已经知道组件路径，也一并给出。不要为了显得完整而粘贴整个项目，相关上下文比数量更重要。

## 看懂最小差异

例如，修改前的组件可能是：

```tsx
export function LearningLink() {
  return <a href="/zh/courses">Browse courses</a>;
}
```

期望的结果是：

```tsx
export function LearningLink() {
  return <a href="/zh/courses">Start learning</a>;
}
```

比较两段代码：显示文字变了，链接地址没有变。任务没有要求换颜色、拆组件或改变路由，这些都不属于这次修改。

<Callout title="先理解，再接受" type="info">
如果你无法解释某一处修改为什么必要，请先让 AI 说明。能运行不代表改动范围正确。
</Callout>

## 在真实页面检查

使用项目 README 中已经记录的启动方式打开页面。找到按钮，确认新文字完整可见，再用鼠标点击以及键盘 Tab、Enter 进行操作，确认仍然进入课程列表。

查看项目差异，核对是否只修改了相关文件。运行项目现有的检查命令，记录实际输出。如果检查失败，先判断是本次修改引起的，还是环境和既有问题；不要把“AI 说通过了”当成验证。

## 动手练习

在一个你能本地运行的练习项目里，选择一个链接或按钮，只修改它的文字。把目标、实际修改和验证结果各写一句话。

- [ ] 新文字与任务要求一致。
- [ ] 原来的点击目标保持不变。
- [ ] 键盘仍可聚焦并操作。
- [ ] 文件差异没有与任务无关的修改。

如果四项中有一项没有证据，就继续检查。确认完成后，再主动使用页面底部的完成标记；阅读到这里本身不会自动完成课时。
