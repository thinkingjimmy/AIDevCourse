## 把生成结果当作待检查的改动

模型可以帮你改代码，也会误解需求、漏掉边界，或把相关文件之外的行为一起改掉。你的工作不是逐行重写它的答案，而是判断这次修改是否真的满足了目标。

本课用三层证据：先看范围，再试行为，最后运行项目里已经有的检查。三层都要有你自己看到的结果，不能用“它说通过了”代替。

## 第一层：差异有没有越界

打开编辑器里的文件差异。先看文件列表，再看具体修改。每一处变化都应该能对应到任务，或者对应到为了完成任务而必须的修复。

| 检查问题 | 为什么要问 |
| --- | --- |
| 是否改到了预期文件？ | 排除改到了另一个相似页面 |
| 是否出现无关配置？ | 避免把环境调整混进功能修改 |
| 是否删掉了原有分支？ | 防止正常路径成功、边界却退化 |
| 是否新增了依赖？ | 确认它确实必要，而且符合项目约定 |

说不清意图的改动，可以请模型用一个具体输入和输出解释。解释仍对不上需求，就要求把范围缩小，而不是让它再加功能。

### 第二层：亲手走一遍

用实际页面执行主要流程，再覆盖一个容易失败的情况。按钮文字要看显示和点击；继续学习要分别看无记录、有记录、最近一课已完成。

不要只走顺利路径。用键盘操作一次，把窗口拉窄再看，刷新之后再做一遍。需要保存的状态，要在重新进入后核对，而不是只看当前画面。

> 构建成功只说明项目还能编过。按钮跳错地方但语法正确时，构建往往仍然是绿的。

## 第三层：运行项目已有的检查

先看项目自己的说明，找到已经配置好的命令。不同项目的脚本不同，不要把下面两行当成所有仓库都有的命令：

```bash
pnpm check
pnpm build
```

只有 `package.json` 里写了对应脚本，这两行才适用。保留实际输出和退出状态。命令没跑、跑到一半被打断、环境缺依赖，都不能写成“已通过”。

<Callout title="测试通过也要看目标" type="info">
自动检查只覆盖它定义过的条件。行为验证不能省。
</Callout>

## 失败时一次只动一个变量

记下第一条有用的错误，以及触发它的步骤。先确认能复现，再请模型解释可能原因和准备改的位置。不要一边改代码、一边升级一大串依赖，否则原因会叠在一起。

修好之后，重跑刚才失败的检查，并回到受影响的主流程看一眼。跟这次修改无关的全量检查不必每次都重复，但也不要靠缩小检查范围来掩盖还没解决的问题。

## 留下可以复核的记录

用三行说明：改了什么、实际做了哪些验证、还剩什么限制。

```text
Changed: the primary link now says Start learning.
Checked: label, destination, keyboard activation, and the project build.
Remaining: mobile Safari has not been checked on a physical device.
```

`Remaining` 不是失败，是你还没证据的部分。把它写出来，比假装全部做过更安全。

## 动手练习

取你已经写好的任务，把每条验收条件换成一个实际操作。改完之后填写观察到的结果，而不是预测结果。只有这些证据足以说明目标已经满足，才把任务标成完成。
