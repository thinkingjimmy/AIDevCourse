## 上下文解决的是理解不一致

模型看到的是你提供的任务、文件和工具结果。它不会自动知道你刚才做过的产品决定，也未必知道某段看似多余的代码在保护什么。上下文的作用，是让同一次任务只有一个理解。

一次小改动通常准备四类信息就够：所在位置、当前行为、期望行为、约束。相关的一小段，比把整个仓库贴进去更有用。

## 四类信息

| 信息 | 需要说明什么 | 一个具体例子 |
| --- | --- | --- |
| 位置 | 在哪里发生 | 课程总览页的开始按钮 |
| 当前行为 | 现在是什么样 | 按钮进入第一篇课时 |
| 期望行为 | 希望怎样变化 | 有学习记录时继续上次未完成的课 |
| 约束 | 必须保持什么 | 没有记录时仍从第一课开始 |

不要把解决方案和目标混在一起。如果你还不确定问题在哪，可以先请模型定位相关代码、说明数据怎么流动，你再决定改哪里。

## 给一个能复现的例子

“继续学习有问题”无法直接验证。你可以写成：完成第一课后进入第二课，关闭页面，再次打开课程总览，点击继续学习。如果仍回到第一课，就把实际结果和预期结果一起给出去。

```text
Location: the course overview page
Current behavior: Continue opens the first lesson every time.
Expected behavior: Continue opens the last unfinished published lesson.
Constraint: without a valid record, open the first published lesson.
Acceptance: test both a new browser session and a returning learner.
```

清楚的例子也会露出边界。上次访问的课如果已经下架，继续入口该去哪一课？在修改之前说清，比实现之后打补丁更容易检查。

<Callout title="约束要具体" type="info">
“别改坏”无法验收。“保持现有 URL，不新增依赖，保留无记录时的第一课入口”才是可以逐项检查的边界。
</Callout>

## 只提供相关的材料

优先给出涉及的页面、组件和数据来源。不确定的文件，先给目录或搜索结果，让模型说明还要读什么。不要粘贴密钥、个人数据，或与任务无关的大段日志。

### 把模糊请求改写一次

拿“帮我改进搜索”这种句子，改成可复现的任务。例如：输入中文的组合阶段，按 Enter 确认候选字时，不应打开搜索结果。

写出复现步骤、当前行为、期望行为，以及要保留的键盘操作。然后请模型先复述。复述仍然含糊，就先补上下文，再进入实现。

## 动手练习

把任务交给一个没有参加前面讨论的人，或者交给一个新的对话。对方如果能回答从哪里开始、怎样算完成、哪些地方不能动，这份上下文就够启动一次小改动。下一模块会把这些条件变成实际检查。
