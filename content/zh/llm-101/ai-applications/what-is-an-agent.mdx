前面我们已经知道，[模型可以请求调用工具](/zh/courses/llm-101/what-is-a-tool)，AI Chat 也可以帮我们[生成和修改交互内容](/zh/courses/llm-101/ai-chat-tips)。

不过这些都是 Chat 产品的功能，现在流行的所谓的智能体（Agent）又是什么？

## <JimmyNoteAnchor id="001">一、Agent 是什么？</JimmyNoteAnchor>

<JimmyNote anchor="001">
  考虑到 Agent 相关的知识相对比较复杂，所以本章节仅会重点讲其核心的部分。其余细节会在 [Agent 101](/zh/courses/agent-101) 课程中详细讲解。
</JimmyNote>

Agent 常被译为「智能体」或「代理」。智能体和 Chat 最大的区别在于 Agent 的 LLM 运行方式从单次静态的生成过程转化为多轮动态生成。

什么意思呢？

前面的课程中我们提到，当用户使用 Chat 产品的时候，模型程序接收到服务器程序的输入后，会进行一系列的计算，然后生成回答。最后，服务器程序将回答传回给 Chat 程序，Chat 程序再将其展示给你。

而 Agent 则稍微有点区别，Agent 程序并不会像 Chat 程序那样直接将模型的回答直接展示给你。而是会先


<KeyTakeaway>
Agent 的关键是：**围绕一个目标，根据执行结果决定下一步。** 写出计划、生成代码或调用一次工具，都不足以说明整个任务已经完成。
</KeyTakeaway>

## 二、模型怎么从「回答」变成「做事」？

还记得工具调用里的「任务单」吗？模型生成调用请求，程序检查请求并执行工具，再把工具结果交给模型。

Agent 把这个过程接成一个可以重复的循环。下面是一个教学示例，并非某个产品的真实执行记录：

| 当前看到的情况 | 下一步行动 | 得到的结果 |
| --- | --- | --- |
| 用户说保存按钮没有反应 | 用浏览器重现问题，并读取相关代码 | 发现点击时出现一条错误 |
| 错误指向一个未定义的变量 | 修改对应代码 | 文件修改成功 |
| 代码已改，但效果还没有检查 | 重新打开网页，填写内容并点击保存 | 页面提示成功，但刷新后内容丢失 |
| 保存结果没有保留 | 检查数据写入过程，再修改和测试 | 刷新后内容仍在，满足本次要求 |

这里最关键的是第三步。**「文件修改成功」只表示文件变了，不表示保存功能已经修好。** 新的测试结果会影响下一次行动。

你也可能听到 **ReAct** 这个词。它来自一项把推理与行动交替结合的[研究](https://react-lm.github.io/)，可以帮助我们理解为什么要根据工具反馈调整行动。它和开发网页界面的 React 框架不是一回事，也不是所有 Agent 必须使用的固定格式。

## 三、Agent 里面有哪些部分？

先不用记复杂的架构，理解下面几部分就够了：

| 部分 | 在保存按钮任务里做什么 |
| --- | --- |
| 目标和要求 | 说明要修复什么，以及怎样才算修好 |
| 模型 | 根据当前信息，生成下一步工具请求或回复 |
| 工具 | 读取文件、修改代码、运行命令、操作浏览器 |
| 上下文和任务记录 | 保存相关代码、已尝试的方法、错误信息和检查结果 |
| 运行程序 | 调用模型、执行获准的工具请求、回传结果，并管理继续或停止 |

真正写入文件、启动浏览器的仍然是程序。模型说「已经保存」，不等于工具真的保存成功；还要看工具返回了什么，以及实际检查的结果。

同样，这个循环通常也不是一边工作一边重新训练模型。工具结果成为下一轮输入的一部分，让模型能够基于新信息继续生成。任务记录能保留多久、是否跨对话保存，则取决于产品的实现。

## 四、AI Chat、工作流和 Agent 怎么区分？

它们可以出现在同一个产品里。聊天窗口是一种交互界面，窗口后面既可以是简单问答，也可以运行一个 Agent。

用保存按钮的例子来比较：

| 方式 | 任务怎样推进 |
| --- | --- |
| 以问答为主的 AI Chat | AI 给出建议，你执行并反馈，再继续提问 |
| 预设工作流 | 程序按事先编排的步骤和分支执行，例如依次检查固定文件、运行指定测试 |
| Agent | 模型根据代码、报错和测试结果，决定下一步检查哪里、用什么工具 |

预设工作流也能使用模型、调用工具和重复执行。区分它们的依据不是步骤多少，而是关键行动由预先写好的规则决定，还是由模型根据现场情况选择。

Agent 也不意味着每个任务都更适合交给它。只需要润色一段文字时，一次回答可能就够了。需要探索问题、尝试操作并根据反馈修改的任务，才更需要这种循环。

## 五、给 Agent 一个能检查的任务

「帮我把网页做好」很难判断是否完成。我们可以把任务说得更具体：

> 请修复这个网页的保存按钮。成功标准是：修改标题后点击保存，页面显示成功提示；刷新页面后，新标题仍然存在。你可以读取和修改这个项目，并在本地浏览器中检查。先不要部署。若需要新的账号权限，或连续两次修改后仍然失败，请停下来说明已尝试的方法和当前问题。

这段要求说明了目标、检查方法、操作范围和停止条件。实际使用时，工具权限还需要由产品或运行程序控制，不能只依赖提示词。

结束时，重点看它交付的结果：修改了哪些地方，做了哪些检查，是否满足你写下的成功标准，还有什么问题没有解决。

不要把「没有报错」「模型说完成了」和「任务达到要求」当成同一件事。即使检查通过，也只说明已经检查的情况通过了。

## 六、试着判断下一步

不需要安装新工具。想一想下面这个情况：

Agent 已经修改代码，并收到了「文件写入成功」的工具结果。它现在能告诉你保存按钮修好了吗？

还不能。它需要按要求操作网页，确认点击后的反馈，再刷新页面检查内容是否保留。如果无法运行浏览器，就应明确说明这一步尚未验证。

你也可以拿一个自己的任务，写下三句话：**我要什么结果、用什么办法检查、遇到什么情况就停止。** 这比只说「你自己想办法完成」更便于执行和验收。
