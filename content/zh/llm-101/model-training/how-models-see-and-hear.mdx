前面我们一直在讲文字：输入文字，模型生成文字。但现在，你也可以给一些 AI 产品上传截图、照片或录音，再让它们回答问题。

这时你可能会想：文字会经过 Tokenizer，变成模型能处理的数字；那一张照片、一段声音，又是怎么进入模型的？

这一讲，我们从同一个思路出发：**让不同形式的信息，变成模型可以计算的数字表示。**

## 一、什么是多模态？

这里的「模态」，可以先理解为信息的形式。文字、图片和音频，就是不同的模态。

**多模态模型**能够处理不止一种形式的信息。例如，同时接收图片和文字，再生成文字回答。

不过，多模态不是一个表示「所有能力都具备」的标签。有些模型支持图片输入，有些支持音频，有些还能生成图像或声音。支持哪种输入、生成哪种输出，需要分别确认。

| 你看到的功能 | 涉及什么能力？ |
| --- | --- |
| 上传照片，询问照片里有什么 | 图片输入与文字输出 |
| 上传录音，整理讲话内容 | 语音识别，或音频理解与文字输出 |
| 输入文字，让产品念出来 | 语音生成 |
| 上传照片，让产品生成另一张图 | 图片理解，以及图像生成或编辑 |

这些能力可能由一个模型完成，也可能由产品里的多个模型配合完成。比如，先把录音转成文字，再交给语言模型整理，就能做出语音笔记功能。

因此，看到产品提供麦克风按钮，并不能据此判断它背后的语言模型可以直接处理声音。

## 二、模型是如何看图的？

先想一下，电脑是怎么保存图片的。

一张图片由很多像素组成，每个像素都有表示颜色的数值。模型接收到的不是人眼看到的那幅画面，而是经过处理的数字数据。

在一种常见的视觉语言模型方案中，可以将过程简化为三个步骤。

**第一步：处理图片，将它划分成适合计算的区域。**

例如，把一张界面截图分成许多小块。模型处理图片时，还需要保留位置相关的信息，否则就很难分清某个按钮在左边还是右边。

实际方案也可能先缩放图片，或对较大的图片切出多个区域。这里的小块只是帮助理解的类比，并不是说每个模型都会采用相同的切法。

**第二步：通过视觉编码器，把图片变成一组数字表示。**

你可以先把编码器理解为一个负责处理图片的计算模块。它会把颜色、边缘、形状等视觉信息转换成后续模型可以使用的特征。

**第三步：让模型结合图片表示与文字问题，生成回答。**

比如你上传截图后问：「右下角的按钮上写了什么？」模型需要结合图片中的信息和你的问题，再生成对应的文字。

[Hugging Face 的视觉语言模型介绍](https://huggingface.co/blog/vlms#technical-details)展示了图像编码器、连接模块和语言模型配合工作的常见结构。不同模型的实现并不完全相同。

<JimmyNote>
  你可以把视觉编码器想成一个负责把画面整理为数字特征的模块。它不一定先写出「这里有一个按钮」这样的文字，再交给语言模型；图片可以通过数字特征参与计算。
</JimmyNote>

这也回答了另一个问题：图片是不是也要先变成 Token ID？

**不一定采用文字那种「查词表、得到 Token ID」的方式。** 很多方案会使用一串图像特征向量，也就是一组组数值。你可能听到别人把它们称为视觉 Token，但不能把它理解为「一小块图片就等于一个汉字」。

## 三、看懂图片，和读出图片里的文字一样吗？

不一样。我们拿一张产品页面截图来举例。

| 你提出的问题 | 主要需要处理什么？ |
| --- | --- |
| 页面上有哪些按钮？ | 识别画面中的元素 |
| 按钮上写了什么？ | 识别图片中的文字 |
| 提交按钮在输入框的哪一侧？ | 判断位置与空间关系 |
| 为什么点击按钮没有反应？ | 还需要运行状态、交互过程或代码等信息 |

模型可能看出这是一个登录页面，却读错某个很小的字；也可能准确读出按钮文字，却判断错位置。

而一张静态截图通常不能提供按钮的真实运行情况。看到按钮是灰色的，可以作为判断线索，但仅凭截图不能确认程序里到底发生了什么。

**所以，能描述画面，不代表所有细节都识别正确，更不代表已经验证了页面功能。**

## 四、模型是如何听声音的？

电脑也会把声音保存为数字。比如，录音会记录声音波形随时间的变化。处理音频时，还可以把它转换成表示不同频率随时间变化的特征。

你不需要记住这些转换方法。重点是：**声音也可以经过编码器，变成模型能处理的一组组数值。**

不过，在产品里常见的语音功能，可能走不同的路径。

### 路径一：先转成文字，再让语言模型回答

这个过程可以简化为：

1. **语音识别。** 将录音中的讲话转成文字，也叫 ASR。
2. **文字处理。** 语言模型根据转写文字，生成摘要或回答。
3. **语音播放。** 如果需要，再通过语音合成，把文字回答读出来，也叫 TTS。

例如，语音识别模块先得到「下周三确认上线时间」，语言模型再把它整理成待办事项。像 [Whisper 的语音识别研究](https://arxiv.org/abs/2212.04356)，就研究了从音频预测转写文本的能力。

这种方案里，语言模型如果只收到转写文字，就不能直接利用未保留在文字中的声音信息。比如背景警报、说话的停顿和语调，可能没有出现在转写结果里。

### 路径二：让模型接收音频表示

另一类方案会让音频经过编码器，再把音频表示与文字指令一起交给模型。它可以处理讲话内容，也可能处理背景声音、音乐等信息，具体取决于模型的能力。

比如 [Qwen2-Audio 的官方介绍](https://qwenlm.github.io/blog/qwen2-audio/)说明了音频编码器与语言模型结合的方案，并展示了语音、声音和音乐分析任务。

即使如此，也不能把声音判断当作确定事实。模型说一段声音「像警报」，与确认具体设备发生了什么，是两件不同的事。

同样，能接收音频，并不自动意味着能生成语音。理解声音和生成声音需要分别确认。

<KeyTakeaway>
  语音转文字、理解音频、生成语音，是不同的能力。选择产品时，要确认它实际接收了什么信息，以及哪些内容会在处理过程中丢失。
</KeyTakeaway>

## 五、搞懂这个概念有什么用？

**第一，把关键内容清楚地交给模型。**

问截图里的某个小字时，可以同时提供整张截图和局部放大图：整图保留位置背景，局部图方便辨认细节。询问一段录音时，可以提供相关时间范围，减少无关内容。

如果重要细节本来就模糊、被遮挡，或者声音已经听不清，模型也可能只能猜测。让它把猜测说得更肯定，并不能找回输入里缺失的信息。

**第二，先确认识别结果，再要求分析。**

例如，先让模型读出图表的标题、坐标和数值，再要求总结趋势；先核对录音中的姓名、日期和金额，再生成会议纪要。底层信息识别错了，后面的分析也可能跟着出错。

**第三，区分看见的事实与推断。**

你可以要求模型分别说明「图中能直接确认的内容」和「还需要补充资料的判断」。例如，截图能显示报错文字，但故障原因可能仍要结合操作步骤和日志来确认。

这不会保证模型每次都分得准确，却能给你一个更容易核对的输出结构。

你可以用一张自己熟悉的页面截图做练习：先问模型有哪些文字和控件，再问它如何改善页面。检查它是否先认对了内容，以及建议中有没有依赖截图里看不到的信息。
