我们聊完了模型是如何预训练的，我们再来聊聊几个大家可能关心的问题：新闻里总说的「开源模型」是什么意思？模型名字里的「60B」是什么？这么多模型，到底哪个更强？我又应该用哪一个？

<JimmyNote>
  模型更新很快，一份具体型号的推荐清单可能很快就会过时。这一讲，我想帮你建立选择模型的方法。以后遇到新的模型，你也能自己判断是否值得试一试。
</JimmyNote>

## Q1：开源和闭源模型有何区别？

你可能经常看到这样的新闻：「某家公司发布了新的开源模型。」

回想上一讲：训练会调整模型内部的大量参数。训练结束后，这些参数的数值会被保存下来，通常称为模型的**权重（Weights）**。你可以把它理解为模型经过训练后得到的一份成果。

**理解开源与闭源模型，可以先看：你能不能拿到这份训练后的权重，并自己运行它。**

闭源模型通常不提供可下载的权重。你通过厂商的聊天产品或 API 使用模型，由服务方负责运行。就像去餐厅点菜，你能吃到做好的菜，但拿不到厨房里完整的做法和准备好的材料。

新闻里常说的开源模型，很多首先是开放了权重。你可以下载这些权重，在合适的电脑或服务器上运行，也可能在许可范围内继续训练。这样就不必每次都通过原厂的服务使用模型。

不过，这里的「开源」需要稍微分清楚。

### 开放权重，不等于完整开源

只公开权重，并不代表同时公开了训练代码、数据处理方法和训练数据的信息。按照 [OSI 的 Open Source AI Definition](https://opensource.org/ai/open-source-ai-definition)，开源 AI 还需要提供代码、足够详细的训练数据信息，并满足使用、研究、修改和分享等自由的要求。

所以，你可以先把「可以下载权重」理解为**开放权重（Open Weights）**。至于开放到了哪一步，需要查看模型说明和许可证。

| 你关心的问题 | 闭源模型 | 开放权重模型 |
| --- | --- | --- |
| 如何使用？ | 通常通过聊天产品或 API | 可自行部署，也可使用托管服务 |
| 谁负责运行？ | 服务方负责 | 自行部署时由你负责；托管时由服务方负责 |
| 能否修改权重？ | 通常不能直接修改 | 可在许可范围内继续训练 |
| 需要付什么成本？ | 订阅费或调用费，也可能有免费额度 | 自行部署要承担硬件、运行和维护成本；托管服务也可能收费 |

有两个容易混淆的地方。

**第一，开源不等于使用时完全免费。** 即使下载权重不收费，把模型运行起来仍需要计算资源。你通过某个平台调用开放权重模型，对方也可能按 Token 收费。能否用于商业产品、修改后如何分发，则要看具体许可证。

**第二，开放权重不等于数据自动留在本地。** 只有在本地运行，并确认应用没有把数据发送到外部服务时，才能按这种方式处理数据。如果你用的是网站、App 或第三方 API，输入仍可能被发送给服务方。

<KeyTakeaway>
  开放程度、是否免费、数据在哪里处理，是三个不同的问题。看到「开源」两个字，先查看权重、许可证和部署方式，再判断它是否符合你的需要。
</KeyTakeaway>

## Q2：模型里的 60B 说的是什么？

你可能见过模型名字里带着 7B、32B、60B 或 70B。这里的 B 是 **Billion，十亿**。所以，60B 通常指这个模型大约有 **600 亿个参数**。

注意，是 600 亿，不是 60 亿。它也不是训练文本的字数、模型能记住的知识条数，或者上下文窗口的大小。

还记得前面用来解释模型计算的公式吗？

$$
y = ax + b
$$

在这个简化公式里，a 和 b 是两个参数。训练就是调整这些参数的数值。真实模型的计算复杂得多，但你可以沿用这个理解：**60B 描述的是模型内部有多少个这样的可学习数值。**

### 参数越多，模型就越强吗？

不能只看这个数字。

在模型结构、训练数据和训练方法相近时，增加参数规模可能带来能力提升。但实际比较的模型往往来自不同团队、不同代际，使用的数据和训练方法也不同。

你可以把参数数量类比为厨房的规模。更大的厨房有空间容纳更多设备，但做出来的菜好不好，还取决于食材、做法和训练。不能只看厨房面积，就判断哪家餐厅更好吃。

因此，一个训练更充分、针对某类任务做过优化的小模型，可能在这类任务上超过更大的模型。**参数量描述规模，实际能力要通过任务来验证。**

### 参数量和电脑能否运行它有什么关系？

参数需要占用存储和内存。假设一个 60B 模型的每个参数用 2 字节保存，仅权重就约占 120 GB；运行时还需要额外空间来处理输入和生成内容。

你也可能看到「4-bit 量化版」。可以先把量化理解为：用更少的位数保存权重，降低内存需求，同时尽量保留模型能力。量化可能影响回答质量，实际效果与方法和任务有关，参见 [Hugging Face 的量化说明](https://huggingface.co/docs/transformers/quantization/overview)。

所以，模型是否适合你的电脑，还要结合权重精度、上下文长度和运行软件判断，不能只看 60B 这个数字。

### 为什么有的模型名字里有两个参数量？

有些模型采用 **MoE（Mixture of Experts，混合专家）** 结构。它有很多组参数，但处理每个 Token 时，只使用其中一部分。

例如，[Qwen3-235B-A22B 的官方说明](https://huggingface.co/Qwen/Qwen3-235B-A22B)中，235B 表示总参数量，A22B 表示每个 Token 激活约 22B 参数。

你可以类比为：厨房里有很多厨师，每道菜只安排其中一部分人来做。这样能减少每次计算的工作量，但其他权重仍需要存放和管理。**不能因为激活的是 22B，就认为它和总参数量为 22B 的模型有相同的运行要求。**

## Q3：如何评判哪个模型更强？

先明确一个问题：**你希望它在哪件事情上更强？**

擅长中文写作，不代表擅长修复代码。能解很难的数学题，也不代表能稳定地从一万条反馈里提取信息。模型的能力很难只用一个分数概括。

### 先通过公开评测缩小范围

公开评测通常有两类。

一类是**标准化测试（Benchmark）**。让不同模型完成一组任务，再按规则评分。比如知识问答、数学解题、代码修复等。它可以帮助我们比较模型在某些任务上的表现。

另一类是**人类偏好评测**。把同一个问题交给不同模型，在隐藏模型身份的情况下，让人选择更喜欢的回答。它有助于观察哪些回答更符合参与者的偏好，但「更喜欢」和「事实更准确」并不是同一个标准。

看评测时，我建议先检查四件事：

1. **测了什么？** 是中文写作、数学、代码，还是综合能力？与你的任务是否接近？
2. **比的是哪个版本？** 同一家公司的不同型号、不同版本，结果可能不同。
3. **条件是否一致？** 是否允许联网、使用工具？给了多少生成空间和尝试机会？
4. **结果是否充分？** 测试题和参与人数是否足够？很小的分差是否在误差范围内？

[Stanford 的 HELM 评测](https://crfm.stanford.edu/2022/11/17/helm.html)就强调同时查看多个场景和指标，包括准确性、稳健性与效率。它提醒我们：比较模型时，需要看到不同能力之间的取舍。

### 再用自己的任务做一次小测试

排行榜可以帮助你挑出候选模型。最终是否适合你，还需要拿真实任务试一下。

假设你经常让模型整理用户反馈。可以选出十条有代表性的反馈，里面既有表达清楚的，也有含糊的、同时涉及多个问题的。然后把同样的材料和要求交给两三个候选模型。

先写好判断标准，再看回答，避免被某段流畅的文字影响判断。

| 判断什么？ | 在用户反馈任务里怎么检查？ |
| --- | --- |
| 准确性 | 有没有曲解原意，或补出用户没说过的原因？ |
| 完整性 | 有没有漏掉重要问题或少数用户的不同意见？ |
| 遵循要求 | 是否按指定分类和格式输出？ |
| 稳定性 | 对容易出错的样本重复测试，是否经常出现同类错误？ |
| 时间与成本 | 等待多久？需要多少人工修改？完成一次任务花多少钱？ |

十条反馈只适合做初步筛选。如果要接入实际产品，还需要扩大样本，覆盖常见情况和失败情况。之前我们也讲过，模型的输出会有随机性，一次答对不能代表每次都可靠。

<KeyTakeaway>
  用公开评测缩小范围，再用真实任务确认效果。选择时同时看结果质量、稳定性、速度和成本。
</KeyTakeaway>

## Q4：我应该使用何种模型？

如果你刚开始学习，我建议先从一个容易使用的聊天产品开始。用你手头的真实任务观察它能做什么、容易在哪里出错。等遇到明确限制，再决定是否换模型或使用 API。

选择时，可以按下面的顺序判断。

### 第一步：明确要完成什么任务

把「我要一个很强的模型」换成一个具体目标。比如：整理访谈记录、检查需求中的遗漏、修改一段代码，或者从截图中找出页面问题。

如果任务需要看图，就先确认模型和所用产品都支持图片输入。如果要处理长文档，就用实际文档检查是否放得进去、是否能准确找到细节。上下文窗口大，只说明能容纳更多 Token，不保证它不会遗漏内容。

### 第二步：明确数据和部署要求

如果资料可以发送给外部服务，可以先比较聊天产品或托管 API，减少自己部署和维护的工作。

如果资料必须在指定环境内处理，就先确认允许的数据流向和服务配置。需要自行部署时，再检查开放权重模型的许可、硬件需求和维护成本。不要仅凭「开源」或「闭源」判断数据是否安全。

另外，上一讲提到，预训练得到的基础模型擅长续写，但未必适合直接对话。自己下载模型时，要看它是否适合对话或指令任务；名字中的 Chat 或 Instruct 可以作为线索，具体仍以模型说明为准。

### 第三步：在质量达标后比较速度和成本

下面是几类可以尝试的起点，最终仍要用实际任务确认效果。

| 你的主要任务 | 可以从哪里开始？ | 重点检查什么？ |
| --- | --- | --- |
| 日常解释、改写、整理短文 | 易用的通用聊天模型 | 是否准确、是否符合你的表达要求 |
| 复杂分析、难题、较难的代码修改 | 推理能力较强的候选模型 | 结果能否验证，等待时间是否可接受 |
| 大量分类、信息提取、固定格式输出 | 先试成本较低、速度较快的小模型 | 达标率、格式稳定性和异常处理 |
| 图片或扫描文档处理 | 支持图像输入的模型与产品 | 小字、表格和版面是否识别正确 |
| 必须在指定环境内处理的资料 | 满足部署要求的模型与方案 | 数据流向、访问控制和运维成本 |

比如，你要把一千条反馈归类。一个大模型单条回答很好，但很慢；一个小模型已经能满足你的分类标准，而且更快。此时小模型就可能更适合这个任务。

反过来，如果一次错误会让你花半天返工，就值得测试能力更强的候选模型。调用费只是成本的一部分，你检查和修改答案的时间也要计算进去。

### 第四步：区分模型和产品带来的效果

你最终使用的通常是一个产品。除了模型本身，产品还可能提供联网搜索、文件处理、代码执行和历史消息管理等能力。

所以，一个产品能准确回答今天的天气，可能是因为它查了天气数据；另一个回答不了，可能是因为没有接入相应工具。不能仅凭这一次结果，就判断底层模型谁更强。

你可以比较产品完成整个任务的效果。如果想比较模型本身，就需要尽量保持输入、工具和运行条件一致。

<KeyTakeaway>
  先明确任务和约束，再比较模型。选择能稳定完成任务、等待时间可接受、总成本合适的方案，不必每次都追排行榜第一名。
</KeyTakeaway>

## 试一试：选出适合你的模型

从你最近的工作中选一个任务，用相同的材料和要求测试两个候选模型。先写下「什么结果算合格」，再记录错误、等待时间，以及需要你修改的地方。

做完这次比较，你就有了第一份属于自己的选型依据。
